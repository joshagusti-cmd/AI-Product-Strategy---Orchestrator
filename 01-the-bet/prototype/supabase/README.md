# Backend — Horizon 1 + 2 (real backend, real model calls, real multi-tenant auth)

This is the real backend behind `01-the-bet/prototype/` — a persistent Postgres database, real multi-tenant auth, and an Edge Function making real Claude API calls. It's committed here for version control and reproducibility; the live copy runs on Supabase.

## What's here

- `migrations/0001_init_governance_schema.sql` — five tables (`agents`, `policies`, `approvals`, `shadow_tools`, `audit_log`) matching the prototype's data shape, seeded with the prototype's original demo data.
- `migrations/0002_reseed_demo_data_function.sql` — the first version of the `reseed_demo_data()` RPC (superseded by 0004/0005 below, kept for history).
- `migrations/0003_add_workspaces_and_multi_tenancy.sql` — adds `workspaces` + `workspace_members`, a `workspace_id` column on every table, and switches every text primary key (e.g. agents' `id: 'research'`) to a composite `(workspace_id, id)` key since ids are now only unique *within* a workspace.
- `migrations/0004_auto_provision_workspace_on_signup.sql` — a trigger on `auth.users` that auto-creates a private workspace (+ pre-seeded agent roster and policies, clean activity history) the moment someone signs in for the first time.
- `migrations/0005_harden_internal_functions.sql` — moves the internal helper functions (`is_workspace_member`, `handle_new_user`, `seed_workspace_config`, `seed_demo_activity`) into a `private` schema so they're usable by RLS policies and the signup trigger but not directly callable via the public REST/RPC API — a real finding from Supabase's own security advisor, fixed here.
- `migrations/0006_orchestrate_rate_limit.sql` — adds a `daily_orchestrate_limit` column on `workspaces` (default 20) and an insert-only `orchestrate_usage` log table, giving every workspace a rolling-24h spend cap on real Claude calls.
- `migrations/0007_teams_and_invites.sql` — adds `workspace_invites` (a member invites a teammate by email) and two acceptance paths: the signup trigger joins a brand-new user straight into the inviting workspace if their email has a pending invite, and the `accept_pending_invites()` RPC (called by the frontend once per session) does the same for an already-registered user invited later. Also adds `list_workspace_members()` (returns a workspace's roster with emails — `auth.users` isn't otherwise exposed) and a delete policy letting a member remove a *different* member from `workspace_members`.
- `migrations/0008_rbac_within_workspace.sql` — makes the `role` column on `workspace_members`/`workspace_invites` real: three roles (`admin`, `compliance_owner`, `analyst`, matching `05-the-guardrails/compounding-system.md`'s governance model), each backed by an RLS policy, not just a UI label. Admin gates agent model reassignment and all team management (invite, revoke, remove, change another member's role); admin-or-compliance_owner gates policy edits and Shadow AI govern/kill decisions; everything else (approving/rejecting, running a Shadow AI scan, orchestrating) stays open to any member.
- `migrations/0009_plan_tiers.sql` — adds a `plan` column on `workspaces` (`free`/`pro`/`enterprise`) and the admin-only `set_workspace_plan(ws, plan)` RPC, the only write path to it — `workspaces` has no client-facing UPDATE policy at all, so a plan change (and the `daily_orchestrate_limit` it sets — 20/100/500 respectively) can only happen through this function. No real billing/payment processing: it's a real, enforced cap change, not a real purchase.
- `migrations/0010_real_spend_telemetry.sql` — adds `orchestrate_call_log`, an insert-only (via the service role key) log table with one row per *individual* real Claude call — up to six per Orchestrate run — carrying the real model and real token counts Anthropic returned. Distinct from `orchestrate_usage` (0006 above), which logs one row per *completed* run purely for the rate-limit check; this logs every call, including ones from a run that later fails, since those tokens were still really billed. Powers the Model Spend Dashboard's "Real Orchestrate spend" panel.
- `migrations/0011_policy_gated_approvals.sql` — adds `run_state` (jsonb) and `resumed_at` (timestamptz) to `approvals`. Wires the Policy Editor to actually gate the real Orchestrate pipeline: when a run pauses at the Core-tier policy's gate, `run_state` holds everything needed to resume it (objective, routing, the steps that already ran) right on the same approvals row a human decides — no separate "pending run" table needed. `resumed_at` stops a paused run from being completed (and billed) twice.
- `migrations/0012_shadow_ai_real_discovery.sql` — adds `requested_model` (text, nullable) to `orchestrate_call_log`. Set only when a real call asked for a model with no real key configured and got silently substituted, so that request leaves a real, queryable trace instead of just a one-off toast. Powers the Shadow AI Audit's real discovery scan.
- `migrations/0013_workflow_history.sql` — adds `orchestrate_runs`, an insert-only (via the service role key) archive with one row per *completed* Orchestrate run — the full deliverable (objective, routing, every agent step, executive summary, findings, recommendations, risk flags, real model/token totals, and whether it paused for policy approval along the way). Distinct from `orchestrate_call_log` (one row per individual agent call, for spend telemetry) and from `audit_log` (a one-line pointer, not the deliverable). Powers `workflow-history.html`.
- `migrations/0014_audit_qa.sql` — adds `audit_qa_log`, an insert-only (via the service role key) table logging every natural-language question asked of the audit trail and its answer, plus how many real log rows were considered and the real token counts. Doubles as the real per-workspace rolling-24h rate limit for `functions/audit-qa/` and as a real, persisted Q&A history.
- `migrations/0015_objective_templates.sql` — adds `objective_templates`. Unlike every telemetry/archive table above, this is user-authored data, not derived from a real Claude call — so it's directly client-writable via RLS (same pattern as `policies`/`approvals`/`shadow_tools`), open to any workspace member. Saves the Command Center's current objective, department/source scope, auto-route setting, and per-agent model picks (`agent_models`, keyed by agent id, matching the shape the Edge Function's `agentModels` request field already expects) as a named, reloadable template.
- `migrations/0016_data_driven_pipeline_agents.sql` — adds `sequence_order`/`is_writer`/`is_risk_gate`/`enabled` to `agents`. The real Orchestrate pipeline (see `functions/orchestrate/index.ts` below) now reads its agents from whichever rows have `sequence_order` set and `enabled = true`, in that order, instead of a hardcoded array — the registry became the pipeline's real source of truth. Two partial unique indexes enforce exactly one `is_writer` and one `is_risk_gate` row per workspace at the DB level. Also fixes a real pre-existing gap: the pipeline's Risk & Compliance Agent never had a registry row at all (the pre-existing "compliance" row is a different, illustrative Fraud-Ops agent from the original case study).
- `migrations/0017_external_agent_connector.sql` — adds `agent_type` (`internal_claude` | `external`), `external_key_hash`, `external_last_seen_at`, `external_note` to `agents`, plus a new insert-only `agent_events` table. Lets a workspace register an agent it runs somewhere else entirely (any stack) and have it report real activity into the same registry/Audit Trail/Approval Queue an internal agent uses — see `functions/agent-events/index.ts` below. Only a SHA-256 hash of each external agent's API key is ever stored; the raw key is generated client-side and shown once at registration (`assets/data.js` `registerExternalAgent`).
- `migrations/0018_workspace_emergency_stop.sql` — adds `emergency_stop`, `emergency_stop_at`, `emergency_stop_by_email` to `workspaces`, plus an admin-gated RPC (`set_emergency_stop`, same "no client-facing UPDATE policy, security-definer RPC is the only write path" pattern as `set_workspace_plan` in migration 0009) that flips the flag, stamps who/when, and writes a real `audit_log` entry either way. The bigger, blunter sibling of migration 0016's per-agent Enabled toggle — checked in both real Edge Functions below (`orchestrate` and `agent-events`) before either can make or resume a real Anthropic call or answer a gate check.
- `migrations/0019_real_dollar_spend_cap.sql` — adds `daily_spend_cap_usd` to `workspaces` (Free $5.00/Pro $25.00/Enterprise $150.00, backfilled from each workspace's existing plan), and extends `set_workspace_plan` (migration 0009) to set it alongside `daily_orchestrate_limit` — one admin-only RPC still the sole write path for both caps. A second, real cap on top of the existing run-count one: today's `orchestrate/index.ts` also sums real `orchestrate_call_log` cost over the same rolling-24h window and blocks a fresh run if either cap is hit, since a run-count cap alone can't catch a workspace burning real budget through unusually complex, long-output objectives at a normal run count.
- `migrations/0020_webhook_notifications.sql` — adds `webhook_endpoints` (one row per workspace: `url`, `enabled`, `created_by`) and `webhook_deliveries` (insert-only via the service role key, one row per real delivery attempt: `event_type`, `url`, `response_status`, `success`, `error_detail`). Unlike `workspaces`' own admin-gated settings (plan, emergency stop), `webhook_endpoints` is a dedicated table an admin owns outright, so it uses the same direct-RLS-policy pattern as `agents`/`policies` (migration 0008) — `private.is_workspace_admin(workspace_id)` gates insert/update/delete directly, no security-definer RPC needed — rather than the "no client UPDATE policy, RPC is the sole write path" pattern `set_workspace_plan`/`set_emergency_stop` use. Any workspace member can read the config (so a non-admin can see notifications are set up); only an admin can write it. Powers `orchestrate/index.ts`'s `fireWebhook` below.
- `functions/orchestrate/index.ts` — a Deno Edge Function that makes **real, independent** Anthropic API calls (forced tool-use for structured JSON output), one per real pipeline agent — by default Research → Finance → Ops → Risk & Compliance → Strategy → Executive Writer — with each agent's prompt including the prior agents' actual output as context. Since migration 0016, the pipeline itself is read from the workspace's real Agent Registry (`loadPipelineAgents`) rather than hardcoded, validated at load time (exactly one writer, exactly one risk gate, writer last) so a bad manual registry edit fails a run loudly instead of silently misgoverning it. Which real Claude model runs each agent is real per-call routing, resolved through a three-level fallback: an explicit per-run override (the Command Center's per-agent dropdown) beats the registry's own declared default model, which beats a fixed, always-real Claude default for that agent's structural role (Opus 4.8 for the risk gate, Sonnet 5 for the rest) — a requested label with no real key configured (e.g. the seeded Finance/Strategy agents' "GPT-4o") falls back for real, every time, and the response's `substitutions` array tells the frontend exactly what ran instead. Automatic routing (`autoRoute: true`, the Command Center's default) works the same way, generalized from fixed per-agent-id defaults to a pipeline *slot* (gather/gate/synth/writer) so it still works whatever the registry's real pipeline shape is — `computeAutoRoute` picks a three-tier cascade (baseline/elevated/high) from a real, deterministic heuristic (risk keywords in the objective text + department/source scope size), mirroring the Leader/Filler/Killer cost-cascade concept in `03-the-margin/cost-curve.md`. The final (Writer) call also synthesizes the executive summary, findings, recommendations, and risk flags from everything the other agents found. Every call also logs its real model + token usage to `orchestrate_call_log` (`logCall`, see migration 0010 above) the moment it completes, regardless of whether the run later fails — including, since migration 0012, the originally-requested label whenever it differs from what really ran, so a silent substitution leaves a real trace the Shadow AI Audit's scan can find. **The Policy Editor's Core-tier policy now really gates this pipeline** (migration 0011 above): right after the risk-gate agent's call, if that policy's autonomy is "Approval-required" or "Two-gate" and its riskFlag scores at or above the policy's threshold, the function inserts a real `approvals` row (with `run_state`) and returns `{ paused: true, approvalId, ... }` instead of continuing — every agent after the gate never runs, so their real API cost is never spent, until a human approves it. A second request carrying `{ resumeApprovalId }` (`handleResume`) looks that approval up, confirms it's `approved` and not already `resumed_at`, and continues the pipeline from right after the risk gate using the stored `run_state` — `runOneAgent` is the one function both the fresh-run loop and the resume loop call, so the two paths can't drift apart. Rejecting the approval just leaves the row `rejected`; nothing further ever calls Anthropic. Both real completion points also archive the run in full — `recordRun` (migration 0013 above) writes one `orchestrate_runs` row with everything `workflow-history.html` needs to redisplay that deliverable later. **Real PII/secrets redaction (`redactSensitive`) runs on the objective before it's ever prompted to an agent and on every agent's title/detail/summary/findings/recommendations/riskFlags text before it's stored or returned** — a deterministic pattern-match pass (SSN, Luhn-validated credit-card numbers, email, phone, known API-key prefixes) that masks matches as `[REDACTED:TYPE]` rather than dropping them, counts every one, merges the counts into the response's new `redactions` array (surfaced to the user the same way `substitutions` already is), and logs a real `audit_log` entry (`logRedactions`) whenever any fire. **The objective also gets real prompt-injection screening (`screenPromptInjection`), before redaction and before anything else touches it** — a deterministic pattern match for imperative instruction-override phrasing, system-prompt extraction attempts, chat-template injection markers, and jailbreak framing, neutralizing a matched span in place as `[FLAGGED:PROMPT_INJECTION]`; it only ever runs once, at intake (not per-agent like redaction), and logs immediately (`logPromptInjectionFlags`, high severity) rather than waiting for a completion point. **A workspace-wide emergency stop is checked first, before any of this** (migration 0018 above, `checkEmergencyStop`): if it's active, a fresh run and a resume are both refused with a 423 until an admin lifts it. **Requires a signed-in session** (see below) — it inspects the caller's JWT `role` claim and rejects anonymous requests with a 401, since these are real, metered API calls. It also enforces each workspace's rolling-24h Orchestrate cap server-side, using the service role key to resolve the caller's workspace and log usage — a client can't raise its own limit or erase its usage history to dodge it, and one Orchestrate run (paused-then-resumed or not) only costs one unit of quota no matter how many real calls it takes. **A second, real dollar cap (`checkSpendCap`, migration 0019 above) is checked right alongside that run-count one** — same rolling-24h window, but summing real cost from `orchestrate_call_log` priced at the identical real Anthropic per-model rates `spend.html`'s own real-spend panel uses, so either cap alone can stop a fresh run. **A configured workspace webhook (`fireWebhook`, migration 0020 above) fires at both real pause points** — the fresh-run loop's `paused` branch and `handleResume`'s own `paused` branch (a resumed run pausing again) — POSTing a real JSON payload (workspace name, objective, risk severity/text, approval id, timestamp) to the admin-configured URL, if one is set and enabled. Best-effort and non-blocking, same discipline as `logCall`/`recordRun`/`logRedactions`: a bad URL, an 8s timeout, or a non-2xx response is caught and swallowed, never breaking the real run that triggered it. Every real attempt, win or lose, is logged to `webhook_deliveries` regardless of outcome; no configured/enabled webhook is a cheap, silent no-op (one lookup, nothing logged). **Every archived step also now carries full prompt visibility** — `runOneAgent` captures the exact `system`/`user` prompt it actually sent to Anthropic as `promptSystem`/`promptUser` on that step, at call time, not reconstructed afterward. No schema change needed (`orchestrate_runs.steps` was already jsonb) — it flows straight through `recordRun` and the paused-run `run_state` alike, and `workflow-history.html` shows it behind a "View prompt" toggle per step, closing the "full prompt/response visibility" audit-depth gap (the "response" half — title/detail/riskFlag, the writer's executiveSummary/findings/recommendations — was already real and shown).
- `functions/audit-qa/index.ts` — a second, self-contained Deno Edge Function (this repo has no shared-imports setup between functions, so the small set of JWT/service-role/workspace helpers is deliberately duplicated from `orchestrate/index.ts` rather than shared) powering the Audit Trail's natural-language Q&A. Fetches this workspace's most recent real `audit_log` rows (up to 300, via the service role key) and makes one real Claude call whose system prompt hands them over verbatim and instructs the model to answer strictly from them — citing the specific entries — and to say so plainly, not invent an answer, when the log doesn't support one. Requires a signed-in session (same 401 gate as Orchestrate) and enforces its own real per-workspace rolling-24h cap (40 questions, `audit_qa_log`, migration 0014 above) — separate from Orchestrate's plan-tied cap, since this is a different, much cheaper real Claude usage surface. Every question and answer is archived in `audit_qa_log` too, so a past answer survives navigating away.
- `functions/agent-events/index.ts` — a third, self-contained Deno Edge Function: the universal external-agent connector's real ingestion endpoint. Unlike `orchestrate`/`audit-qa`, it's **not** gated by a Supabase JWT (`verify_jwt: false` at deploy) — the caller is someone else's backend code running an agent Aiven doesn't execute, which has no Supabase session at all. Instead it's authenticated by the external agent's own API key: the incoming key is SHA-256-hashed and matched against `agents.external_key_hash` (migration 0017), which resolves the calling agent's workspace — the key itself *is* the identity, same as any bearer-token API. Two real actions: reporting activity (optionally with a `riskFlag`, evaluated against the exact same Core-tier policy `orchestrate` uses — a flag that crosses the threshold creates a real `approvals` row, same table, same Approval Queue) and `check_approval` (a real, poll-based status check an external agent's own code can call before proceeding on a gated action). Every reported event is stored in `agent_events` and mirrored into `audit_log`, so it shows up in the existing Audit Trail UI with no separate view to build. Aiven can't force an external agent to call `check_approval` or honor its answer — that's the one honest limit on gating something it doesn't run itself. The same workspace-wide emergency stop `orchestrate` checks (migration 0018 above) is checked here too (`isEmergencyStopped`): while active, `check_approval` always answers `"pending"` regardless of the row's real status, and any reported risk flag gates on the spot regardless of the Core policy's threshold. Every reported title/detail/riskFlag.text also runs through the identical `redactSensitive` pass `orchestrate` uses (duplicated, per this repo's no-shared-imports convention) before any of it is stored in `agent_events`, `approvals`, or `audit_log`.

## The multi-tenancy model

- **One public "Demo Workspace"** (`00000000-0000-0000-0000-000000000001`) — readable by anyone, including anonymous visitors (the anon key), but writable only by its own members. In practice: anonymous visitors get a **read-only** view of the shared demo; every write action (model reassignment, policy save, approve/reject, govern/kill, orchestrate) requires signing in.
- **Every signed-in user gets their own private workspace on first sign-in** — auto-created and pre-seeded (agent roster + policies; approvals/shadow tools/audit log start empty), via the `handle_new_user` trigger, unless they were already invited (see below). Their reads and writes are scoped entirely to that workspace, isolated from the demo and from every other user's workspace by RLS (`is_workspace_member(workspace_id)`).
- **A workspace member can invite a teammate by email** (the "Workspace" button in the auth widget, which opens a modal covering team + plan settings). The invite is matched by email, not a token/link — the teammate just needs to sign in (or sign up) with that same email, and `private.accept_pending_invites_for()` joins them to the workspace automatically, either from the signup trigger (brand-new user) or from the `accept_pending_invites()` RPC the frontend calls on every session (already-registered user invited later). A user can belong to more than one workspace this way; the auth widget shows a workspace switcher once they do.
- **Auth is email magic-link (no passwords)** via `supabase.auth.signInWithOtp()`. There's no separate account/org management UI beyond the Workspace modal — no company name, no real billing entity, just workspaces, their members, and a plan.

## Security posture

RLS is on for every table, with real per-workspace isolation now (a real improvement over the original wide-open "anon full access" policies from Horizon 1's first pass). What's still simplified, and would need work before real customer data:

- **Teams/invites and RBAC are both real now** — a member invites a teammate by email with a chosen role and they join automatically; an admin can change any other member's role or remove them from the Workspace modal. Still simplified: no invite expiry, no re-sending a revoked invite without creating a fresh one, and no self-service "leave workspace" or role change (an admin can't demote themselves — avoids locking a workspace out of admins by accident, but also means there's no way to hand off sole-admin status without a second admin already in place).
- **RBAC is three flat roles, not a hierarchy or custom permissions** — `admin` (agent model reassignment + all team management), `compliance_owner` (policy edits + Shadow AI govern/kill decisions — `admin` can do these too), and `analyst` (everything else: approve/reject, run a Shadow AI scan, orchestrate). There's no way to define a custom role or grant one specific permission outside these three bundles.
- **Orchestrate's spend cap is now tied to a real plan tier** — every workspace has a `plan` (Free/Pro/Enterprise → 20/100/500 runs per rolling 24h), changeable by an admin from the Workspace modal via `set_workspace_plan`, still enforced by the Edge Function itself using the service role key. Still simplified: **no real billing/payment processing** — "upgrading" just changes the enforced cap immediately; there's no Stripe, no invoice, no card on file, and nothing stops an admin from "upgrading" for free.
- **Orchestrate is now six sequential calls, so a run takes longer (~30–60s vs. ~10–30s) and any one agent's failure fails the whole run** — there's no partial-credit result if, say, the fourth of six calls errors. The upside: usage is only recorded against the workspace's quota after the final (Writer) call succeeds, so a failed run never costs quota — but a slow or flaky Anthropic response now has more chances to interrupt a run than the old single-call version did.
- **Model routing is real but Claude-only** — the Command Center's per-agent model dropdown genuinely changes which model runs that agent's call. Two of its four options (GPT-4o, Gemini 1.5 Pro) aren't real, since only an Anthropic key is configured; picking either falls back to that agent's Claude default rather than erroring, and the frontend surfaces a toast naming the substitution. True multi-provider support is still open.
- **Automatic routing is a real but simple heuristic, not a risk model** — `computeAutoRoute` only sees the objective's text and how many departments/sources are in scope; it has no access to real transaction data, prior run history, or the kind of scored risk signal `03-the-margin/cost-curve.md`'s Leader-tier model actually produces. It's a genuine deterministic cascade (same input always gives the same tier), explainable in the response, and a real first implementation of "cost-based automatic model routing" — just not a claim of true risk assessment.
- **The policy gate is real but has one pause point, and a simple severity mapping** — Low/Medium/High map to fixed numbers (25/60/90) compared against the policy's threshold, same honesty as auto-routing above: deterministic and explainable, not a trained score. And a "Two-gate" policy only gets one real pause (before Strategy/Writer) — the Killer tier's true second gate (separate approval to *distribute* the finished deliverable) isn't modeled, since the Command Center has no "send externally" action to gate a second time. A paused run's `run_state` also rides on the same `approvals` row any workspace member can already read/write (RLS: migrations/0003) — no new access was granted, but it does mean the objective/routing of a paused run is visible to the whole workspace, same as everything else in the Approval Queue.
- **Shadow AI discovery is real but scoped to this workspace's own data** — the scan reads the real `agents` table (which of the six real agents declare a model this backend can't call) and real `orchestrate_call_log.requested_model` (which real runs actually asked for one anyway). Both are genuine findings, not invented — but that's the ceiling: it can't see outside tool use (a personal ChatGPT account, an unsanctioned browser extension) since nothing about those ever touches this app. Real coverage of that needs actual endpoint/CASB integration and a real design-partner audit — a GTM step, not something this migration/Edge Function change does.

## Two manual steps (can't be done by a coding agent)

### 1. The Anthropic API key

The `orchestrate` and `audit-qa` functions both need `ANTHROPIC_API_KEY` as a secret — it's a project-level secret, shared by every Edge Function in the project, so this is one setup step, not one per function:

1. Supabase dashboard → this project → **Project Settings → Edge Functions → Secrets**
2. Add `ANTHROPIC_API_KEY` with a real key from https://console.anthropic.com/
3. No redeploy needed — each function reads it via `Deno.env.get` on every invocation.

### 2. Allow the site's URL as an auth redirect

Magic-link sign-in redirects back to the page the user started from. Supabase only allows redirecting to URLs on an allowlist:

1. Supabase dashboard → this project → **Authentication → URL Configuration**
2. Set **Site URL** to the GitHub Pages URL (e.g. `https://joshagusti-cmd.github.io/AI-Product-Strategy---Orchestrator/`)
3. Add the same URL (and `.../index.html`, `.../agents.html`, etc., or a wildcard like `https://joshagusti-cmd.github.io/AI-Product-Strategy---Orchestrator/*` if the dashboard supports it) under **Redirect URLs**.

Until this is set, clicking a magic link will fail to return the user to the site with a valid session.

## Reproducing this elsewhere (new project, or after a reset)

With the [Supabase CLI](https://supabase.com/docs/guides/cli) linked to a project:

```bash
supabase link --project-ref <your-project-ref>
supabase db push                              # applies migrations/*.sql in order
supabase functions deploy orchestrate --no-verify-jwt=false
supabase functions deploy audit-qa --no-verify-jwt=false
supabase secrets set ANTHROPIC_API_KEY=sk-ant-...
```

Then update `SUPABASE_URL` and `SUPABASE_ANON_KEY` in `../assets/data.js` to point at the new project, and complete the two manual steps above (API key secret + auth redirect URL) for the new project.
